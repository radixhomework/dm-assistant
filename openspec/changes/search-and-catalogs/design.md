## Context

The record store exists (P1–P2): `entities` carries `tags text[]` (storage-only so far), `fields` JSONB validated against the Zod template registry, no `search_vector`, no source concept. The `search`, `audit` and `external-refs` modules are empty scaffolds. The admin panel (AdminPage) already hosts users, instance settings and the calendar editor as stacked sections. The Lore page lists categories; the shell header exists (`RootLayout`) but hosts no search. PRE-SPEC §2 deferred the text-search dictionary to this change and still describes the index as "title + `body`" — but the record-editor change removed the generic body field, so the indexed content is title + template-declared text fields (prose, short text).

Revised after DM review (2026-11-21), then after the DM answered the four open points (2026-11-22): the import becomes a web UI in a tabbed admin panel, catalog provenance becomes a registry of named sources, imports preview their overwrites (per-item checkboxes with a select-all control), the dataset format follows Open5e, the admin Tags tab gains rename/merge management, and the external-references feature is folded into this change (roadmap row updated accordingly).

## Goals / Non-Goals

**Goals:**

- Accent-insensitive full-text search over all records, immediately consistent with saves.
- A DM-driven import UI (file or API endpoint) with preview-before-overwrite, named sources, and one-time unit conversion.
- Tags as a working surface (edit, display, inventory, filter) plus an admin tab with rename/merge management.
- The external-references deep-link catalogue (sources, entries, badges, Reference channel) — PRODUCT §3.5 lands here.
- A queryable `[TO BE SPECIFIED: …]` inventory hosted in the audit module, report-only.

**Non-Goals:**

- MCP tools (`search_records`, `list_tags`, `list_missing`) — P5; the services built here are what they will call.
- Multilingual search, stemming dictionaries, content-language anything (decision 2026-11-09).
- Copying external-site content — the reference catalogue stores links only (GOVERNANCE §4).
- Automatic gap resolution, scheduled imports, import triggered by the AI (charter rule 6).
- Fauna/Flora/Treasure-types datasets — no Open5e equivalent; those catalogs stay DM-created (Internal). Beasts→Fauna mapping is a later extension.

## Decisions

1. **Text-search configuration: `simple` extended with `unaccent`, one custom configuration.** The migration creates `CREATE EXTENSION IF NOT EXISTS unaccent;` then a configuration (e.g. `simple_unaccent` copied from `simple`, mapping `word`/`hword`/`hword_part` through the `unaccent` dictionary), used for both indexing (`to_tsvector`) and queries (`websearch_to_tsquery`). Rationale: mixed fr/en content rules out `french`/`english` stemming (each mangles the other language); `simple` + unaccent is the standard single-configuration answer and satisfies the acceptance test (`ecole` finds `École`). Alternatives: `french` dictionary (rejected — wrong on English SRD imports), `english` (rejected — wrong on French prose), per-record dictionaries (rejected — reintroduces the multilingual search the 2026-11-09 decision removed). No stemming means exact-token matching; plural-form misses on prose are accepted for v1 (title lookups keep the trigram path below); revisiting is a parking-lot note, not a spec change.

2. **Service-maintained `search_vector`, no DB trigger.** The indexed field set is template-driven (prose + short-text keys per type, known only to the TS registry), so a trigger would duplicate that knowledge in SQL and drift. The entities service computes `setweight(to_tsvector(cfg, title), 'A') || setweight(to_tsvector(cfg, joined_text_fields), 'B')` in the same write transaction as create/update; a shared `buildSearchVector(record)` helper (in `app/src/search/`, importing the registry from `packages/schemas`) is also reused by the migration backfill. Markdown syntax is indexed raw (the tokenizer discards markup characters). Alternatives: Postgres trigger with hardcoded field lists (rejected — drift risk), generated column (impossible — needs JSONB path knowledge per template), no index + sequential scan (rejected — fine at tiny scale, wrong forever after).

3. **Recall helper: title ILIKE as a secondary match path.** `websearch_to_tsquery` matches whole tokens only; a partial title (`gar` → `Gardon`) would miss. The search endpoint ORs the tsvector match with `title ILIKE '%q%'` (the pattern the list endpoint already uses for autocompletion). ILIKE is case-insensitive but accent-sensitive — accent-insensitive matching always goes through the tsvector path, which the acceptance scenarios exercise. **Title-first is enforced explicitly** (CodeRabbit review, round 1): `ts_rank` alone does not guarantee the spec's promise across multiword queries (a fields-only record matching two lexemes can outrank a title record matching one), so the ordering groups by an explicit `title_matched` flag (vector title match OR ILIKE title match) before rank and title. The A/B weights stay: they order within the title and fields groups.

4. **Provenance = a registry of named sources, not an enum.** New table `catalog_sources(id, name, attribution text NULL, disabled_at timestamptz NULL)`; `entities.source_id` nullable FK, populated only for the 8 catalog types. The registry seeds exactly one built-in source, **Internal / Interne** (immutable name, not deletable, not disableable); administrators create, rename and disable named external sources (rename keeps provenance history honest — the badge shows the current name; disable only removes the source from import selection). REST creation always binds catalog records to the Internal source — the client cannot declare external provenance (prevents forgery); only the import binds external sources. Source is set at creation and never rebindable — the single exception is the confirmed cross-source import overwrite, which rebinds the record to the importing source so the badge always names the data's true origin (CodeRabbit round-1 review). Attribution notes are per source and rendered on the attribution page under the fixed WotC statement. Alternatives: fixed `srd`/`unearthed_arcana` enum (rejected — the DM wants arbitrary named sources), a text column without registry (rejected — badges, attribution and import selection need a real entity), reusing the future `external_sources` deep-links table (rejected — different lifecycle; convergence possible later, not now).

5. **Source-data read-only enforcement lives in the application service** (golden rule, ARCHITECTURE §4): `entities.service.update/delete` reject writes to the source-derived fields of catalog records bound to an external source, and reject their deletion, with a stable error code (translated client-side per PRE-SPEC §1). The DM-authored fields (Pitch, Private description) stay editable on imported records — the mapping leaves them to the DM, and rejecting them would make the imported sheet a dead end (CodeRabbit round-1 review). Any future adapter (the P5 MCP) inherits the guardrail by calling the same service. The UI offers the DM-field editing and hides the source-field edit and delete actions (the entity response carries its source). The Internal source stays fully editable. Alternatives: whole-record lock (rejected — strands the DM-authored fields), controller-level guard (rejected — the invariant must live below the adapters), DB trigger (rejected — service is the single enforcement point per architecture).

6. **Import = admin UI, two origins, preview-before-import.** The admin panel's Import catalogs tab posts to an admin-only import endpoint with: origin = uploaded JSON file or HTTPS endpoint URL (server-side fetch, admin-only guard, HTTPS scheme enforced, private/internal addresses refused — basic SSRF hygiene for a self-hosted single-operator instance), target catalog, source. Parsing accepts a bare array or the Open5e envelope (`results[]` + `next` pagination, followed server-side with a page cap). The service layer runs **dry-run by default**: parse → validate each element against the Open5e shape → map to catalog fields → validate against the catalog template schema → match by slug → return the preview (new / same-source overwrite pre-checked / different-provenance conflict unchecked (another external source or Internal) / slug-collision-skipped with reasons). The preview carries a select-all control over every selectable element (DM request — bulk decisions stay two clicks). Confirming the preview executes one transactional write of the accepted elements and returns the report. A failing element never blocks the run — it is skipped and reported; execution stays all-or-nothing for the *accepted* set (no half-written run). The dry-run/confirm split is a two-call protocol (preview token or re-post) kept stateless: the confirm call re-validates everything — no server-side preview session. Alternatives: CLI script (rejected by DM review — replaced by the UI), REST import without preview (rejected — silent overwrites), scheduled imports (rejected — human action).

7. **Matching key: the slug, carried by the Open5e key.** Open5e objects carry a stable `key` (slug-charset); it maps to our immutable `entities.slug`, which is unique per instance. Matching rules in the preview: same slug within the target catalog → match (overwrite pre-checked only for a record imported from the same source; a record from another external source or Internal stays unchecked until explicitly selected); slug taken by a record of *another* type → impossible (unique-slug constraint), element skipped and reported (the DM renames or removes it in the dataset). The slug survives title renames on Open5e, so re-imports match stably. Alternatives: external UUID (rejected — Open5e v2 objects' ids are not stable across their datasets and adds a hidden identifier to our schema), title matching (rejected — titles change, slugs don't).

8. **Unit conversion at import, in the schemas package.** A `convertSrdUnits` helper (next to the Statistics block vocabulary) applies the barème (5 ft = 1.5 m · 1 mile = 1.5 km · 1 lb = 500 g · 1 gal = 4 l) to dimensional values, reading the world's configured units from `settings` and identity-converting when the world already uses imperial. Exact barème arithmetic — no rounding heuristics. Alternatives: converting at display time (rejected — the templates mandate one-time conversion at import), leaving SRD values imperial (rejected — the world's units govern).

9. **Open5e mapping: fixed per catalog, templates untouched.** `name` → title, `key` → slug, the `descriptions[]` entry for the chosen document (default document `srd-2024`, selectable in the UI; fallback to `desc` for flattened exports) → Public description as markdown (paragraphs joined); Pitch and Private description stay empty (DM-authored — the application never rewrites or splits source prose, charter rule 1); mechanical extras are not imported in v1 (catalog templates carry no statistics block except Fauna/Flora, both outside v1 import). The mapping lives in `packages/schemas` (Zod-validated Open5e object shapes + mappers), documented in `docs/srd-import.md`. Shaping the catalog templates after Open5e was rejected: the templates are the DM's data model and the structure must stay source-agnostic. Endpoint-to-catalog targets (verified against Open5e v2): `/classes/`, `/species/` (2014: `/races/`), `/conditions/`, `/damagetypes/`, `/languages/` — documented, not hard-wired (the DM pastes any endpoint; the shape validation decides).

10. **Admin panel reorganized into tabs.** AdminPage content moves to tabs — Users, Instance, Calendar (existing sections relocated) — plus the new Import catalogs tab (decision 6) and the consultative Tags tab (decision 11). Access rules unchanged (admin-only endpoints and pages, `dm` denied — accounts-and-admin delta carries the MODIFIED requirement). Tabs are client-side navigation on one admin route; no new route tree.

11. **Tags tab: management actions on a DM-wide read path.** `GET /api/tags` remains authenticated for all DM accounts (it feeds Lore/search filters and editor completions); the admin Tags tab renders the same data with per-tag record links and adds two admin-only instance-wide actions (DM request): **rename** rewrites every record carrying the tag via `array_replace` plus a service-side dedup pass (a record carrying both old and new values must not end up duplicated), and **merge** removes the absorbed tag while adding the target where missing — one transaction each, reporting the touched record count. Alternatives: per-record edits scripted by hand (rejected — the DM asked for one-click instance-wide hygiene), soft/alias tags (rejected — parking-lot complexity, v1 wants hard rename/merge).

12. **Gap inventory = query-time scan in the audit module.** The inventory endpoint scans stored records at query time reusing the same text-field extraction helper as search indexing, applying the marker regex `/\[TO BE SPECIFIED(?::[^\]]*)?\]/g` (case-sensitive literal). Single-world scale (hundreds of records) makes scan-at-query correct and always fresh; the P5 audit change can move to a maintained structure if it grows. The audit module owns the service and endpoint now; dead links/orphans/violations land there in P5. Resolution is the DM's edit — the endpoint and page offer no write path, honoring charter rule 2.

13. **Search and gaps are shell pages outside the Lore sidebar contract.** Header search entry → `/search`; Lore page link → `/gaps`. Neither alters `app-shell-navigation` (the sidebar enumerates Lore-section pages, records, and specific exclusions; these two pages simply are not in that set, like Admin/Account). `ts_headline` snippets are configured with explicit delimiters and rendered by splitting into React nodes — never `dangerouslySetInnerHTML`.

14. **Attribution page lands with the import.** GOVERNANCE §4 makes the WotC attribution an implementation obligation once SRD content enters the instance — the page (`/attribution`, linked from the settings screen and external-source badges, fr + en labels) shows the fixed SRD 5.2 CC-BY-4.0 statement followed by the instance's external sources with their optional attribution notes.

15. **External references: links only, two surfaces, one registry.** The ARCHITECTURE §5 tables land as designed: `external_sources (id, name, url_template, enabled)` and `external_refs (source_id, kind, name, url)`. The catalogue stores **links only** — no content is fetched or copied from the sites (GOVERNANCE §4; the url_template prefills the manual-add form and resolves `{name}` at add time, never at render). The two render surfaces: badges on a record sheet driven by an accent/case-insensitive **exact title match** against entry names (computed per sheet read, entries of disabled sources excluded — no association work for the DM, and "no match, no badges" keeps sheets clean), and the editor's **Reference button** opening a lookup-only panel (search + source/kind filters, links open `noopener` in a new tab — nothing is inserted into content). The `external-refs` module (scaffolded in P0) hosts sources/entries CRUD, the admin bulk import (JSON file of `{kind, name, url}` targeted at one source; update-on-same-kind+name, create otherwise, never delete — consistent with the catalog import) and the DM-wide read endpoint feeding both surfaces. The registry stays deliberately separate from `catalog_sources` (decision 4): provenance and deep-link sites have different lifecycles — convergence stays a parking-lot note. Alternatives: mention-driven badges (rejected — conflates lore mentions with game-element lookups, heavier), DM-linked refs per record (rejected — the DM asked for render-time badges without association work), copying summaries from 5e.tools/aidedd (rejected — GOVERNANCE §4: we link, we don't copy).

## Risks / Trade-offs

- [No stemming reduces prose recall (plurals, verb forms)] → accepted for v1; title trigram path covers the dominant lookup pattern; revisit in the parking lot if the DM reports misses (a config swap is one migration, no spec change).
- [`unaccent` + custom configuration needs superuser privileges] → migrations already run as the compose `postgres` superuser; the configuration creation is idempotent.
- [Server-side URL fetch (SSRF surface)] → admin-only endpoint, HTTPS enforced, private/internal address ranges refused, page cap on pagination following; the operator's reverse proxy adds nothing to reach from the app container.
- [Open5e API availability/shape drift at import time] → endpoint mode is best-effort (error surfaced in the preview); the file mode is the offline fallback; the documented shape is pinned to Open5e v2 and versioned in `docs/srd-import.md`.
- [Slug uniqueness across catalogs blocks some imported elements] → per-element skip + report in the preview (never a global abort); the DM resolves in the dataset or renames the local record.
- [Search vector write amplification on every save] → negligible at single-world scale; the JSONB walk is bounded by the registry's field list.
- [ILIKE path is accent-sensitive] → documented secondary path only; the accent-insensitive guarantee rests on the tsvector path the scenarios exercise.
- [Marker regex false negatives if the DM hand-writes variants] → the canonical marker is a structured convention; the inventory documents the exact matched forms rather than guessing variants.
- [Query-time gap scan cost] → bounded by instance scale; revisit only if profiling says so (P5 audit restructure).
- [Badge title-match false positives (two different records sharing a normalized name)] → exact normalized match only, source-labeled so ambiguity is visible; per-record manual override stays a parking-lot note if the DM hits a collision.

## Migration Plan

Three incremental migrations, one per consuming round (branches merge to main round by round — the DM asked for short-lived branches instead of a single ten-day PR): **R1** `feat/search-foundations` (unaccent + `simple_unaccent` + `search_vector` + GIN + backfill), **R3** `feat/catalog-sources-import` (`catalog_sources` + seed Internal + `entities.source_id`), **R4** `feat/external-references` (`external_sources` + `external_refs`). Each migration runs on a fresh database in a test and keeps main deployable at every merge. Rollback: standard migration down / backup restore; no data is destroyed — the new columns and tables are derived or additive.
